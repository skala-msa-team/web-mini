# 프로젝트 한계점 및 추후 AI 실제 결합 로드맵

## 문서 목적

현재 프로젝트의 운영·AI 기능 한계를 정리하고, 향후 개발 범위로 Amazon Bedrock 기반 AI 서비스를 실제 업무에 결합하기 위한 단계별 방향을 제시합니다.

현재 구현된 내용과 추후 계획을 구분하며, 아직 구현 또는 검증되지 않은 항목은 `추후 예정`, `추가 필요`, `미검증`으로 표시합니다.

본 프로젝트는 AI가 최종적인 법률 판단이나 판결을 대신하는 것을 목표로 하지 않습니다. AI는 관련 문서와 판례를 검색하고 근거를 정리하는 보조 역할을 수행하며, 최종 판단과 책임은 사람이 담당합니다.

## 실제 AI 결합 로드맵

### 1단계. AI 연동 기반 구축

Spring Boot에서 Amazon Bedrock Agent Runtime API를 호출할 수 있는 기본 기반을 구축합니다.

- AWS IAM Role과 최소 권한 정책 정의
- Spring Boot용 Bedrock Client 구성
- Agent ID와 Alias 관리 방식 정의
- 요청·응답 DTO 및 예외 응답 정의
- timeout과 재시도 기준 설정
- 기본 Agent 호출 테스트 작성
- CloudWatch 로그 연결

완료 판단 기준:

- 인증정보를 소스 코드에 저장하지 않고 Agent 호출 가능
- 성공·실패·timeout 응답 구분 가능
- 기본 호출 테스트 반복 통과

미정 사항:

- 사용할 Foundation Model
- Agent별 실제 Prompt
- 동기 응답과 비동기 응답 방식

### 2단계. RAG 문서 파이프라인 구축

법률·판례·내부 문서를 검색하고 AI 답변에 신뢰할 수 있는 근거를 제공합니다.

- S3 문서 저장 구조와 파일명 규칙 정의
- 문서 유형과 Metadata 정의
- 문서 버전과 개정일 관리
- 문서 수집·갱신·삭제 정책 정의
- Bedrock Knowledge Base 구성
- OpenSearch Serverless Vector Store 연결
- 문서 검색 결과와 출처 확인

완료 판단 기준:

- 질문에 대해 관련 문서 검색 가능
- 검색된 문서의 제목과 버전 확인 가능
- 문서 변경 시 재색인 절차 정의

미정 사항:

- 허용할 문서 형식
- 문서 Chunk 크기와 분할 기준
- 문서별 접근 권한

### 3단계. Agent 역할과 Workflow 정의

재판관·변호사·판사 Agent의 책임과 호출 순서를 명확히 정의합니다.

- 역할과 책임
- 입력 데이터
- 참조 문서 범위
- 출력 JSON Schema
- 다른 Agent와의 관계
- 실패 시 처리 방식
- 사람의 검토가 필요한 조건

Spring Boot가 Agent 호출 순서와 결과 통합을 담당하는 Orchestrator가 될지, Bedrock 내부 Workflow에서 처리할지 비교한 뒤 결정합니다.

완료 판단 기준:

- Agent별 역할이 중복되지 않음
- Agent 간 입력·출력 계약 문서화
- 충돌하는 결과 처리 기준 정의

### 4단계. 답변 근거와 구조화된 응답 제공

AI 답변뿐 아니라 답변의 근거와 검토 필요 여부를 함께 제공합니다.

- 답변 요약
- Agent별 의견 또는 분석 결과
- 참고 문서명
- 문서 버전과 개정일
- 페이지·문단 또는 Chunk 위치
- 근거의 적절성
- 추가 검토 필요 여부
- 법률 자문이 아니라는 안내 문구

자유 형식 문자열 대신 JSON Schema를 사용해 Frontend가 답변·근거·경고를 안정적으로 표시할 수 있도록 합니다.

완료 판단 기준:

- 모든 답변에 근거 문서 연결
- Frontend가 답변·근거·경고를 각각 표시 가능
- 근거가 없을 때 임의로 답변하지 않고 검토 필요 상태 반환

### 5단계. AI 품질 및 안전성 검증

AI가 얼마나 정확한지뿐 아니라 잘못된 답변과 위험한 입력을 어떻게 처리하는지 검증합니다.

- 테스트 질문 데이터셋 작성
- 기준 답변과 필수 근거 정의
- RAG 검색 품질 평가
- 환각과 출처 불일치 검사
- Prompt Injection 테스트
- 개인정보 입력 및 마스킹 테스트
- 금칙 질문과 답변 거부 기준 정의
- 사람이 결과를 검토하는 절차 마련

평가 지표:

- 답변 정확성
- 질문과 답변의 관련성
- 근거 문서의 적절성
- 출처 일치 여부
- 환각 발생 여부
- JSON Schema 준수 여부
- Agent 역할 수행 여부
- 응답 시간
- 호출 비용

### 6단계. 운영 안정화

AI 응답 지연, 외부 서비스 오류, 과도한 호출량에 대응할 수 있도록 운영 구조를 보완합니다.

- 긴 작업의 비동기 처리
- 작업 상태 저장과 상태 조회 API
- timeout 및 재시도 정책
- 중복 요청 방지
- 실패 상태와 사용자 안내 메시지 정의
- 사용자·기능별 호출량 제한
- 토큰 사용량과 비용 모니터링
- CloudWatch 로그·메트릭·알람 구성

### 7단계. 운영 데이터 기반 개선

실제 사용 과정에서 발견되는 검색 실패와 답변 오류를 개선합니다.

- 자주 실패하는 질문 분석
- 검색되지 않는 문서 분석
- 잘못된 답변 사례 수집
- 사용자 피드백 반영
- Prompt와 Agent Workflow 개선
- 문서 Metadata와 Chunk 기준 개선
- 평가 데이터셋 지속 업데이트

실제 사용자 질문과 법률 정보는 개인정보 및 민감정보 보호 정책에 따라 익명화하거나 필요한 기간만 보존합니다.

### 8단계. 고가용성과 확장

싱글 인스턴스 중심의 초기 운영 구조를 고가용성 구조로 확장합니다.

- EC2 Single Instance에서 Auto Scaling Group으로 전환
- ALB 도입
- 다중 AZ 배치
- RDS Multi-AZ 구성
- Blue-Green 또는 Rolling 배포
- 자동 Rollback
- 장시간 AI 작업을 위한 Queue 도입 검토
- 반복 요청을 줄이기 위한 Cache 도입 검토
- 장애 복구 훈련과 복구 목표시간 정의

## 현재 구조와 목표 구조

현재 구조:

```text
사용자 브라우저
  -> Vue Frontend
  -> Nginx Reverse Proxy
  -> Spring Boot
  -> PostgreSQL
```

운영·AI 결합 후 목표 구조:

```text
사용자 브라우저
  -> Vue Frontend
  -> API Gateway
  -> Spring Boot Orchestrator
  -> Bedrock Agents
  -> Bedrock Knowledge Base
  -> OpenSearch Serverless Vector Store
  <- S3 법률·판례 문서
```

## 발표용 핵심 메시지

1. 현재 프로젝트는 로컬 데모와 Mock AI 중심으로 구현되어 있으며, 실제 운영 환경과 AI 품질 검증은 추후 개발 범위입니다.
2. AI 결합은 단순히 Agent API를 호출하는 것이 아니라, 신뢰할 수 있는 문서 구축과 RAG 검색 품질, Agent 역할, 근거 제공, 안전성 검증을 함께 구현하는 과정입니다.
3. 향후에는 AI 호출과 품질을 운영 데이터로 검증한 뒤, Auto Scaling, Multi-AZ, 무중단 배포를 적용해 안정적인 실제 서비스로 확장합니다.

## 발표용 마무리 문장

본 프로젝트는 현재 서비스의 기본 운영 구조를 기반으로, 향후 Bedrock Agent와 RAG를 단계적으로 결합하는 방향으로 확장할 수 있습니다. AI를 최종 판단의 주체로 사용하기보다는 신뢰할 수 있는 근거를 제공하는 보조 시스템으로 발전시키고, 품질·보안·비용·고가용성을 검증한 뒤 실제 운영 범위를 확대할 예정입니다.
