Backend Issue #205

WebSocket · STOMP · Demo 사용자 연결 계획

이 문서는 chore/backend-205-websocket-stomp-demo-identity 브랜치에서 진행할 백엔드 작업 순서를 바로 따라갈 수 있게 정리한 실행용 체크리스트다. 이번 이슈의 핵심은 REST가 아니라 STOMP 인프라 구성이다. 도메인 서비스 상세 구현은 다른 이슈에서 붙고, 여기서는 연결 규칙과 메시지 통로를 먼저 고정한다.

이번 이슈에서 끝내야 하는 것
/ws handshake /app publish /topic subscribe /user/queue/errors
완료 판단
2 Browser

두 브라우저에서 같은 재판 채널에 연결하고, 정상 메시지와 개인 오류 Queue까지 확인한다.

Scope

작업 범위

  • /ws 핸드셰이크 엔드포인트
  • /app, /topic, /user/queue/errors 브로커 규칙
  • X-Demo-User-Id 검증과 STOMP 세션 연결
  • Heartbeat, 허용 Origin, 메시지 크기 기본값
  • Demo STOMP 명세와 동일한 Destination 유지
Out of Scope

이번 이슈에서 안 하는 것

  • 재판 도메인 규칙 계산
  • DB Entity, Migration, JPA 저장 구현
  • 프론트 STOMP Client 연결 화면
  • 실제 Judge, Vote, Trial 비즈니스 로직
Key Contract

고정해야 할 경로

CONNECT /ws 필수
SEND /app/trials/{trialId}/chat 필수
SUBSCRIBE /topic/trials/{trialId}/chat 필수
SUBSCRIBE /topic/trials/{trialId}/events 필수
SUBSCRIBE /user/queue/errors 필수
Execution Order

단계별 구현 순서

1

기존 공통 Demo 사용자 코드 재사용 지점 확인

  • #207에서 만든 Demo 사용자 식별/검증 클래스를 그대로 재사용한다.
  • 새로 UUID 규칙을 만들지 말고, WebSocket 세션 속성에 같은 값을 넣는다.
  • 핵심 질문: HTTP Header 검증 로직을 Handshake 단계로 어떻게 옮길지 결정.
2

STOMP 기본 설정 추가

  • WebSocketMessageBrokerConfigurer 구현 클래스를 추가한다.
  • registerStompEndpoints 에서 /ws 와 허용 Origin을 설정한다.
  • configureMessageBroker 에서 /app, /topic, /user 를 연결한다.
  • Heartbeat와 메시지 크기 기본값을 설정한다.
3

연결 식별: Handshake 또는 Channel Interceptor

  • X-Demo-User-Id 가 없거나 형식이 틀리면 연결을 막는다.
  • 정상 값이면 session attribute 또는 Principal에 Demo 사용자 식별값을 저장한다.
  • 이 값이 이후 @MessageMapping 처리에서 조회 가능해야 한다.
4

에러 전달 규칙 고정

  • 잘못된 CONNECT, SEND, payload 검증 실패를 /user/queue/errors 로 보낸다.
  • 형식은 공통 에러 Envelope로 맞추고, 최소 code, message, destination, occurredAt 를 포함한다.
  • REST 예외 처리와 STOMP 예외 처리를 섞지 말고, 메시징 전용 핸들러를 분리한다.
5

메시지 핸들러 스캐폴딩 추가

  • @MessageMapping("/trials/{trialId}/chat") 정도의 최소 엔드포인트를 만든다.
  • 지금은 서비스 로직 대신 계약 검증, 사용자 식별 조회, 브로드캐스트 구조만 맞춘다.
  • 브로드캐스트는 /topic/trials/{trialId}/chat 와 /topic/trials/{trialId}/events 를 사용한다.
6

검증과 확인

  • ./gradlew check 로 기본 검증.
  • 앱 실행 후 두 브라우저 또는 두 탭으로 CONNECT → SUBSCRIBE → SEND 시나리오 확인.
  • 헤더 누락, 잘못된 UUID, 허용되지 않은 메시지에서 개인 오류 Queue 수신 확인.

Coding Notes

코드 작성 포인트

  • REST용 공통 응답 래퍼를 STOMP payload에 그대로 복제하지 말고, 명세에 맞는 이벤트 Envelope를 별도로 둔다.
  • Demo 사용자 검증 로직은 중복 구현하지 말고 공통 Validator 또는 Factory를 주입받아 쓴다.
  • Principal 이름을 Demo 사용자 ID로 두면 이후 메시지 처리에서 접근이 단순해진다.
  • 에러 전송 시 전체 stack trace나 내부 예외 문구를 그대로 노출하지 않는다.
  • 허용 Origin은 현재 로컬 프론트 개발 주소만 열고, 와일드카드 사용은 피한다.
Definition of Done

완료 체크리스트

  • /ws 로 STOMP CONNECT가 성립한다.
  • X-Demo-User-Id 가 메시지 처리 단계에서 조회된다.
  • /app/trials/{trialId}/chat SEND가 브로드캐스트 경로와 연결된다.
  • 잘못된 연결/메시지가 /user/queue/errors 로 전달된다.
  • 두 브라우저 동시 연결 확인 결과를 남긴다.
Recommended Start

바로 시작할 순서

1. #207에서 만든 Demo 사용자 공통 코드를 읽고, WebSocket에서 재사용할 지점을 정한다. 2. WebSocketStompConfig 를 만든 뒤 /ws, /app, /topic, /user 를 고정한다. 3. Handshake/Channel interceptor로 X-Demo-User-Id 를 세션에 심는다. 4. 최소 @MessageMapping 과 개인 오류 Queue를 붙인다. 5. 마지막에 두 브라우저 연결과 실패 케이스까지 검증한다.
